# Schema settings

## Summary

`src/schema-settings/` implements the schema settings dialog and everything that opens it: one palette command, one `file-menu` item and a toolbar button (see the [README](../../README.md#schema-settings)). The dialog edits a pure draft model; saving writes the base edits through `SchemaWriter` in one write and then migrates renamed and removed property keys in the member notes.

## Responsibilities

- **Registration** ([schemaSettings.ts](../../src/schema-settings/schemaSettings.ts)): `registerSchemaSettings(plugin, env, registry)` adds the `checkCallback` command `open-schema-settings` ("Open schema settings", available on an active `.base`), a `file-menu` item "Schema settings" for `.base` files from the sources `tab-header`, `more-options` and `file-explorer-context-menu`, and installs the toolbar button through `installSchemaButton()` ([Internals](./internals.md)). Open failures show a `Notice`. One dialog per plugin instance: opening again closes the previous one, and `plugin.register()` closes it on unload, so a plugin reload leaves no dialog with stale handlers behind.
- **Opening** (`buildSchemaSettings(plugin, env, registry, basePath, viewName)`, async, pure apart from reading the vault; `registerSchemaSettings()` opens the modal with its result): reads the base source, collects the member frontmatter keys (they become native field rows), the other `.base` paths as relation targets, `otherDefinitions(registry, membership, basePath, name)` (other schema bases defining a field name, each with the count of this base's members also in that base), and the modal state from `schemaState()` (known fields via `knownFieldDrafts()`, or the parse error of an invalid base or unreadable file). `viewName` picks the preselected view (`defaultViewIndex`, first view if null or unknown); the toolbar button passes the view switcher label, command and file menu pass null. Each field's detected type id comes from `metadataTypeManager.getTypeInfo(name, null).expected.type` (`detectedTypeOf()`), the selectable types and their labels from `listPropertyTypes(getMetadataTypeManager(app))` ([Internals](./internals.md)), passed as `input.types`. While collecting member keys it also maps each lower-cased key to the member values; `input.memberValues(name)` reads that map (empty when members are unknown).
- **Dialog** ([SchemaSettingsModal.ts](../../src/schema-settings/SchemaSettingsModal.ts)): `SchemaSettingsModal` is a wide modal (`.improved-bases-schema-modal`, built with Obsidian DOM helpers and components only, no UI framework) laid out as a dense table: a toolbar (search filtering rows by name, the "Add new fields to" dropdown with more than one view, "Add field", which clears the search so the new row is visible), a column head and one grid row per known field with a disclosure chevron, the inline name input, a type box in which a bare `<select>` covers the whole box (so a click anywhere opens it) with the Lucide icon and a chevron floating above it without taking clicks (the choices come from `typeChoices(draft, input.types)`, the selected one from `typeChoice(draft, input.types)`, a change goes through `applyTypeChoice()`; labels and icons are the registry's (`propertyTypeOf()`), so they follow Obsidian's language, "Native" labels the `native` entry when Obsidian's type is unknown and an unregistered override reads `<id> (not registered)`), a details column (up to three option color dots and the count for a select; the target base's icon, its path and a "Multiple" tag for a relation; a "Type override" tag for a native field with a schema entry, else a dash) and the remove button. `onOpen()` blurs whatever Obsidian focused first, so the dialog opens without a focused field. Next to the modal title, in Obsidian's `.modal-header`, a "Default entry icon" input edits the base's own icon (`input.icon`, passed trimmed as the third `onSave` argument, "" = none; the hint about the system emoji picker is its tooltip; see [Schema base](../concepts/schema-base.md)). Only `relation` and `select` rows expand (switching to one of them opens the panel): a relation shows "Related base" as the same kind of box (a `<select>` over `input.basePaths`, plus the saved target when its file is gone, with a disabled "Choose base" placeholder until one is picked; the icon shows the target base's default entry icon via `input.baseIcon(path)` and `renderIcon()`, else the generic `lucide-layout-list`) and "Allow multiple" (`ToggleComponent`); a select shows its options as chips (color dot plus value; a click opens `openOptionEditMenu()` from [Widgets](./widgets.md) with Rename, which swaps the chip for an inline input, Remove, and the colors) followed by "+ Option", which turns into an inline input (Enter adds and reopens it, Escape or an empty blur turns it back), and the toggle. Warning rows under a field (orange, with icon) hold the rename hint (`referencesName()`) and the conflict hint (`conflictHint()` over `input.otherDefinitions(name)`, advising without blocking the save: "Also defined in Meetings.base as text; 1 note is in both bases."; select options and colors do not count) and the mismatch hint (`mismatchHint()` over `input.memberValues(originalName ?? name)`, advising without blocking: "5 notes have a Status that is not a valid Zahl; they keep their value and show as Text"); all are shown without expanding and toggle `has-warning`. Removing a known field turns the row into an inline confirmation "Remove 'X' and its value from N notes?" (N from `countAffected`) and then into a struck-through row with Undo; remove and rename are refused while `membersKnown()` is false. The footer status line reports pending renames and removals ("1 pending rename · Role → Position") or, without any, that Save writes the base and migrates the notes; errors appear below it. Its buttons follow a dirty check (`snapshot()` of drafts and icon against the opening state): a single Close while nothing changed, Cancel and Save otherwise; the error state shows Close next to Reset. Rows are validated with `validateDrafts()` before Save. For a base with an invalid schema it shows the parse error and a "Reset schema" button with a confirm step. Styling uses Obsidian tokens and classes only (`--size-*`, `--radius-*`, `--font-ui-*`, `--background-modifier-*`, `--color-*-rgb`; `search-input-container`, `dropdown`, `checkbox-container`, `mod-cta`, `clickable-icon`) so themes restyle the dialog; the footer has no background of its own so it takes the theme's modal surface (Cupertino's is translucent).
- **Draft model** ([schemaDraft.ts](../../src/schema-settings/schemaDraft.ts), pure): `FieldDraft` (with `detected`, Obsidian's type id for the property or null, `override` the native entry overriding Obsidian's type, kept unchanged while its type is not changed, `removed`) / `OptionDraft`, `knownFieldDrafts()` (union of all views' `order`, `properties:` keys, member keys and schema fields; current view's order first, rest alphabetical; fields without a schema entry are native), `validateDrafts()` (empty or padded names, reserved names only for new or renamed fields, case-insensitive duplicates, swapped renames, a live field taking a removed field's name, relation needs an existing base or its already saved target, option values and colors), `typeChoices(draft, types)` / `typeChoice(draft, types)` / `applyTypeChoice(draft, choice)` (the dropdown model over the registered `PropertyType[]`: `native` first only when the detected type is not selectable, i.e. reserved or unregistered, then every unreserved registered id as `native:<id>`, then the override's id when it is not registered, then `relation` and `select`; the shown choice is the override, else the detected type when selectable, else `native`; choosing `native` or the detected id drops the override, another id writes `{ type }`, plugin types keep their details), `conflictHint(draft, others, label)` (`label` names a native type id for the hint, the modal passes the registry name), `mismatchHint(draft, types, values)` (null unless a native draft overrides with a registered type that has `validate`; counts non-empty values it rejects, a throwing check counts as valid; names come from `propertyTypeOf()`, a null detected type reads "as is"), `draftsToEdits(drafts, originalNames, addView)` (returns `ColumnEdits` plus the schema mutation: native drafts delete their plugin entry unless it overrides the type; untouched entries keep their key spelling), `removals()`, `renames()` (changed names including case-only), `renameKey()` (moves one frontmatter key by exact name, as in YAML; `renamed`, `missing` or `conflict`).
- **Save** (`onSave(drafts, addView, icon)` from `buildSchemaSettings()`): writes `draftsToEdits()` and the base icon with one `writer.update(basePath, mutate, edits, icon)` call (activation is implicit), then `migrateRenames()` renames the keys in the member notes whose frontmatter on disk has an old key (read via `cachedRead`, not the metadata cache; unparseable frontmatter is passed on and ends as `failed`), sequentially through `fileManager.processFrontMatter`, skipping notes that already have both keys, and `removeProperties()` deletes removed keys from the members in one pass, matching keys case-insensitively (Obsidian treats `Status` and `status` as one property) and reporting counts per name; an unreadable note counts as `failed` instead of aborting. `renameSummary()` and `saveSummary()` build the notice: rename counts, removed counts, and "Filters or formulas still reference 'X', update them manually"; when the members are unknown nothing is renamed or removed and the notice says so.
- **Reset**: `onReset` calls `writer.reset()` which replaces the whole `improved-bases` value with an empty schema ([Schema](./schema.md)).
