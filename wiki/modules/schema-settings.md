# Schema settings

## Summary

`src/schema-settings/` implements the schema settings dialog and everything that opens it: one palette command, one `file-menu` item and a toolbar button (see the [README](../../README.md#schema-settings)). The dialog edits a pure draft model; saving writes the base edits through `SchemaWriter` in one write and then migrates renamed and removed property keys in the member notes.

## Responsibilities

- **Registration** ([schemaSettings.ts](../../src/schema-settings/schemaSettings.ts)): `registerSchemaSettings(plugin, env, registry)` adds the `checkCallback` command `open-schema-settings` ("Open schema settings", available on an active `.base`), a `file-menu` item "Schema settings" for `.base` files from the sources `tab-header`, `more-options` and `file-explorer-context-menu`, and installs the toolbar button through `installSchemaButton()` ([Internals](./internals.md)) on demand: the returned `SchemaSettingsHandle` has `setToolbarButton(visible)`, which [main](./plugin-core.md) calls with `settings.showToolbarButton` (idempotent; unload removes the button). Open failures show a `Notice`. One dialog per plugin instance: opening again closes the previous one, and `plugin.register()` closes it on unload, so a plugin reload leaves no dialog with stale handlers behind.
- **Opening** (`buildSchemaSettings(plugin, env, registry, basePath, viewName, focus?)`, async, pure apart from reading the vault; `registerSchemaSettings()` opens the modal with its result): reads the base source, takes the members from `env.membership.targetEntries(basePath)`. `Membership` watches only schema bases and relation targets, so for a base without `improved-bases:` yet the dialog opens at once and `input.members` holds a background `firstResult(env.query, basePath)` ([Query](./query.md)), never cut short: it resolves to the drafts including the notes' properties, or null when the scan failed (members stay unknown). Until then `membersKnown()` is false and the member values are empty. The read list wins over Membership afterwards, because Membership's first result after Save may still be partial; the same source feeds Save migrations and `countAffected` (`readMembers()` collects keys and values), collects the member frontmatter keys (they become native field rows), the other `.base` paths as relation targets, `otherDefinitions(registry, membership, basePath, name)` (other schema bases defining a field name, each with the count of this base's members also in that base), and the modal state from `schemaState()` (known fields via `knownFieldDrafts()`, the parse error of an invalid base or unreadable file, or a read-only error state without reset for a base whose schema declares a newer format version, see [Schema base](../concepts/schema-base.md)). `viewName` picks the preselected view (`defaultViewIndex`, first view if null or unknown); the toolbar button passes the view switcher label, command and file menu pass null. Each field's detected type id comes from `metadataTypeManager.getTypeInfo(name, null).expected.type` (`detectedTypeOf()`), the selectable types and their labels from `listPropertyTypes(getMetadataTypeManager(app))` ([Internals](./internals.md)), passed as `input.types`. While collecting member keys it also maps each lower-cased key to the member values; `input.memberValues(name)` reads that map (empty when members are unknown).
- **Focus**: `registerSchemaSettings()` returns `{ open(basePath, viewName, focus?) }`; `focus = { name, type }` (a type id, mapped by `choiceOf()` to `select`/`relation`/`native:<id>`) is used by the header type change. `focusDraft()` finds the draft case-insensitively or creates it like "Add field", applies the choice unless already shown, the modal expands the row and scrolls to it. The preset makes the dialog dirty; closing without saving discards it. `typeChoices()` omits `select`/`relation` from the native entries (they are registered property types now) so the dropdown has no duplicates.
- **Dialog** ([SchemaSettingsModal.ts](../../src/schema-settings/SchemaSettingsModal.ts)): `SchemaSettingsModal` is a wide modal (`.improved-bases-schema-modal`, built with Obsidian DOM helpers and components only, no UI framework) laid out as a dense table: a toolbar (search filtering rows by name, the "Add new fields to" dropdown with more than one view, "Add field", which clears the search so the new row is visible), a column head and one grid row per known field with a disclosure chevron (an Obsidian `clickable-icon` made with `iconButton()` like the remove button, because `.is-tablet button:not(.clickable-icon)` pads plain buttons to 40px and squeezed the icon out of its 24px column; its `svg` has `flex: none`, so a theme that pads `.clickable-icon` with more specificity than two classes, Cupertino's 10px, cannot shrink it either; the two icon columns are the custom properties `--ib-disclosure-col`/`--ib-remove-col` on `.improved-bases-schema-modal`, `--touch-size-s` under `.is-mobile`, where chevron and remove button take that size too, the chevron as `button.improved-bases-field-disclosure` so the removed row's placeholder span in the same column keeps its height; `refresh()` mirrors the open state into `aria-expanded` next to `is-open`), the inline name input, a type box in which a bare `<select>` covers the whole box (so a click anywhere opens it) with the Lucide icon and a chevron floating above it without taking clicks (the choices come from `typeChoices(draft, input.types)`, the selected one from `typeChoice(draft, input.types)`, a change goes through `applyTypeChoice()`; labels and icons are the registry's (`propertyTypeOf()`), so they follow Obsidian's language, "Native" labels the `native` entry when Obsidian's type is unknown and an unregistered override reads `<id> (not registered)`), a details column (up to three option color dots and the count for a select; the target base's icon, its path and a "Multiple" tag for a relation; a "Type override" tag for a native field with a schema entry, else a dash) and the remove button. While `input.members` is pending, a line above the table (`.improved-bases-members-loading`, spinning loader) says "Reading the notes of <base>… Suggestions from notes appear when done."; on success the line goes, the notes' fields are added behind the known ones and before fields added in the dialog (`addMemberFields()`, also added to the opening snapshot so they do not count as a change) and the list re-renders with the suggestions; on failure the line turns orange with "Could not read the notes of this base, so there are no suggestions from notes.". `onOpen()` blurs whatever Obsidian focused first, so the dialog opens without a focused field. Next to the modal title, in Obsidian's `.modal-header`, a "Default entry icon" input edits the base's own icon (`input.icon`, passed trimmed as the third `onSave` argument, "" = none; the hint about the system emoji picker is its tooltip; see [Schema base](../concepts/schema-base.md)). Only `relation` and `select` rows expand (switching to one of them opens the panel): a relation shows "Related base" as the same kind of box (a `<select>` over `input.basePaths`, plus the saved target when its file is gone, with a disabled "Choose base" placeholder until one is picked; the icon shows the target base's default entry icon via `input.baseIcon(path)` and `renderIcon()`, else the generic `lucide-layout-list`) a "View" select below it (`input.viewNames(base)` = `baseViewNames()`; options "All entries" (default, no `view`) plus the target's views, the saved view kept as an option when it no longer exists; changing the base resets it; a stale async fill is dropped; written as `view` by `draftToField()`; the details column shows `base › view`) and "Allow multiple" (`ToggleComponent`); a select shows its options as chips (color dot plus value; a click opens `openOptionEditMenu()` from [Widgets](./widgets.md) with Rename, which swaps the chip for an inline input, Remove, and the colors) followed by "+ Option", which turns into an inline input (Enter adds and reopens it, Escape or an empty blur turns it back), then a suggestion row "In notes:" (`renderSuggestions()` over `optionSuggestions(values, options)`: the distinct strings of `input.memberValues(originalName ?? name)`, lists flattened, that are not options yet (values pending removal from the notes and the old names of renamed options are left out), most frequent first with their counts, at most 12, as dashed chips that add the value with the next palette color (`nextOptionColor()`) on click, plus "Add all (n)" when there are at least two; hidden when nothing is left). Switching a native list type (`LIST_TYPES`: multitext, tags, aliases) to select or relation sets `multiple` in `applyTypeChoice()`, and the toggle. Warning rows under a field (orange, with icon) hold the rename hint (`referencesName()`) and the conflict hint (`conflictHint()` over `input.otherDefinitions(name)`, advising without blocking the save: "Also defined in Meetings.base as text; 1 note is in both bases."; select options and colors do not count) and the mismatch hint (`mismatchHint()` over `input.memberValues(originalName ?? name)`, advising without blocking: "5 notes have a Status that is not a valid Zahl; they keep their value and show as Text"); all are shown without expanding and toggle `has-warning`. Removing a known field turns the row into an inline confirmation "Remove 'X' and its value from N notes?" (N from `countAffected`) and then into a struck-through row with Undo; remove and rename are refused while `membersKnown()` is false. The footer status line reports pending renames and removals ("1 pending rename · Role → Position") or, without any, that Save writes the base and migrates the notes; errors appear below it. Its buttons follow a dirty check (`snapshot()` of drafts and icon against the opening state): a single Close while nothing changed, Cancel and Save otherwise; the error state shows Close next to Reset. Rows are validated with `validateDrafts()` before Save. For a base with an invalid schema it shows the parse error and a "Reset schema" button with a confirm step. Styling uses Obsidian tokens and classes only (`--size-*`, `--radius-*`, `--font-ui-*`, `--background-modifier-*`, `--color-*-rgb`; `search-input-container`, `dropdown`, `checkbox-container`, `mod-cta`, `clickable-icon`) so themes restyle the dialog; the footer has no background of its own so it takes the theme's modal surface (Cupertino's is translucent).
- **Draft model** ([schemaDraft.ts](../../src/schema-settings/schemaDraft.ts), pure): `FieldDraft` (relations carry `view`; with `detected`, Obsidian's type id for the property or null, `override` the native entry overriding Obsidian's type, kept unchanged while its type is not changed, `removed`) / `OptionDraft`, `knownFieldDrafts()` (union of all views' `order`, `properties:` keys, member keys and schema fields; current view's order first, rest alphabetical; fields without a schema entry are native), `validateDrafts()` (empty or padded names, reserved names only for new or renamed fields, case-insensitive duplicates, swapped renames, a live field taking a removed field's name, relation needs an existing base or its already saved target, option values and colors), `typeChoices(draft, types)` / `typeChoice(draft, types)` / `applyTypeChoice(draft, choice)` (the dropdown model over the registered `PropertyType[]`: `native` first only when the detected type is not selectable, i.e. reserved or unregistered, then every unreserved registered id as `native:<id>`, then the override's id when it is not registered, then `relation` and `select`; the shown choice is the override, else the detected type when selectable, else `native`; choosing `native` or the detected id drops the override, another id writes `{ type }`, plugin types keep their details), `conflictHint(draft, others, label)` (`label` names a native type id for the hint, the modal passes the registry name; a definition differing only in the relation `view` counts as conflict only when `shared > 0`, i.e. notes are in both bases), `mismatchHint(draft, types, values)` (null unless a native draft overrides with a registered type that has `validate`; counts non-empty values it rejects, a throwing check counts as valid; names come from `propertyTypeOf()`, a null detected type reads "as is"), `draftsToEdits(drafts, originalNames, addView)` (returns `ColumnEdits` plus the schema mutation: native drafts delete their plugin entry unless it overrides the type; untouched entries keep their key spelling), `removals()`, `renames()`, `optionMigrations()` (per kept select field, under its new name: option renames from `OptionDraft.original` to `value` and the values with `removal === "notes"`) (changed names including case-only), `renameKey()` (moves one frontmatter key by exact name, as in YAML; `renamed`, `missing` or `conflict`).
- **Save** (`onSave(drafts, addView, icon)` from `buildSchemaSettings()`; when any rename, removal or option migration fails for a note, the summed count becomes an event warning `warning.saveFailed` for the base in `env.warnings` and the notice ends in "(see warnings)"): writes `draftsToEdits()` and the base icon with one `writer.update(basePath, mutate, edits, icon)` call (activation is implicit), then `migrateRenames()` renames the keys in the member notes whose frontmatter on disk has an old key (read via `cachedRead`, not the metadata cache; unparseable frontmatter is passed on and ends as `failed`), sequentially through `fileManager.processFrontMatter`, skipping notes that already have both keys, and `removeProperties()` deletes removed keys from the members in one pass, matching keys case-insensitively (Obsidian treats `Status` and `status` as one property) and reporting counts per name; an unreadable note counts as `failed` instead of aborting. `renameSummary()` and `saveSummary()` build the notice: rename counts, removed counts, and "Filters or formulas still reference 'X', update them manually"; when the members are unknown nothing is renamed or removed and the notice says so.
- **Option migration** (in `onSave`, after the field rename/remove steps): option renames and removals are marked in the draft, not applied at once: `OptionDraft` carries `original` (the saved value, null for a new option) and `removal` (`"notes"` or `"schema"`, null while live); `liveOptions()` filters the removed ones, which show struck through. Removing a new option drops it; removing a saved one asks for "Remove from notes" / "Only remove from schema" (`removeOption()`). On Save `migrateOptions()` runs `migrateOptionValues(app, files, field, optionValueEdit(renames, removals), previousKey)` ([optionMigration.ts](../../src/schema/optionMigration.ts), see [Schema](./schema.md)) once per note per field, so swaps and chains stay intact; notes whose field rename hit a conflict are skipped (counted as conflict), and `optionSummary()` adds "Option values updated in N notes" to the notice.
- **Warnings section**: `SchemaSettingsInput.warnings` is the snapshot `env.warnings.forBase(basePath)` at open time, rendered by `renderWarnings()` above the toolbar (`.improved-bases-dialog-warnings`, one `renderWarningRow()` per entry without base links); `dismissWarning(id)` removes an event warning from the registry and the row. `defaultIcon` (the plugin setting) is the placeholder of the base icon input.
- **Reset**: `onReset` calls `writer.reset()` which replaces the whole `improved-bases` value with an empty schema ([Schema](./schema.md)).

## Phone

Under `.is-phone` the dialog body scrolls as a whole (toolbar, column head and field rows together, so the fields get the screen); only the title with the default-icon line above it stays put. The footer is hidden while the drafts are not dirty (`updateStatus()` toggles `is-dirty`, and `is-error` for the error dialog, which keeps its footer); the resting text "Changes are written to the base on Save…" then shows as `.improved-bases-hint` block above the toolbar and scrolls away. A dirty footer is sticky (`position: sticky; bottom: 0`) with the full pending-changes text and Cancel/Save at touch height. The toolbar wraps (search and "Add field" in one row, the "Add new fields to" dropdown below it) and the dialog may use the full dynamic viewport height. The details column stays hidden below 700px as before; the expanded panel is single-column.
